# ADR-0001：采用渐进式重构

日期：2026-08-18
状态：已接受

## 背景

现有服务包含大量 PHP 业务代码、Workerman/Swoole 通信逻辑、Redis 队列和生成的 Protobuf 类，但原始 `.proto` 尚未找到。一次性用 Go 重写会同时承担协议恢复、业务理解、数据迁移和上线切换风险。

## 决定

- 使用 Go 新建协议网关，优先隔离设备连接、帧和 Protobuf 处理。
- 在行为和测试覆盖足够之前保留 PHP 成熟业务。
- 使用版本化事件和 API 连接 Go、PHP 与 Python AI 服务。
- 按业务能力逐步迁移，不以代码行数作为迁移进度指标。

## 结果

优点：可以尽早获得 Go 网关收益，保持现有业务连续性，并让每个迁移步骤可回滚、可对比。

代价：迁移期需要维护多语言服务、契约和部署；短期系统复杂度高于单体重写。

## 被否决方案

- 立即全量 Go 重写：协议和业务事实不完整，验收依据不足，风险过高。
- 永久保持 PHP 单体：不利于隔离长连接、AI 批任务和独立扩容。
- 全部使用 Python：AI 生态有优势，但不作为高连接密度协议网关的首选。

## 复审条件

当协议恢复、关键业务回放测试和容量测试完成后复审服务边界；如果 PHP 保留部分已足够小且有完整契约测试，可决定最后迁移或长期保留。
