# AI 微信客服开发路线图

最后更新：2026-08-19

## 总体原则

按“先确认事实、再建立协议闭环、再迁移业务、最后接入 AI”的顺序推进。每一阶段都必须有独立任务文档、可运行的验证和可回滚交付，不用代码量衡量进度。

## 阶段与验收门

| 阶段 | 任务 | 预计时间 | 可验收交付 |
|---|---|---:|---|
| 0 | 项目治理与架构基线 | 已完成 | 跨 AI 规范、架构、成本与安全边界 |
| 1A | 旧源码安全与迁移审计 | 2–4 天 | 模块、依赖、许可证、秘密风险、运行入口和迁移清单 |
| 1B | 恢复最小 Protobuf 协议 | 4–8 天 | 可编译 `.proto`、消息类型映射、PHP/Go 双向兼容样本 |
| 2 | Go 协议网关最小闭环 | 2–3 周 | TCP 拆包、鉴权、心跳、入站/出站消息和回放测试 |
| 3 | 业务与数据桥接 | 2–3 周 | 标准事件、PostgreSQL、Redis、outbox 和 PHP 兼容适配 |
| 4 | AI 客服辅助 MVP | 2–3 周 | 分类、检索、建议回复、人工确认、模型费用审计 |
| 5 | 长期记忆与知识库 | 2–3 周 | `MemoryService`、Agent Memory 试点、文档检索与删除链路 |
| 6 | 自动回复与质量系统 | 2–4 周 | 风险分级、低风险自动回复、离线评估和人工反馈闭环 |
| 7 | 生产化与容量验证 | 2–4 周 | 高可用、监控、备份、安全测试、压测和灰度发布 |
| 8 | 时序知识图谱（可选） | 2–4 周 | Graphiti/Neo4j 试点及效果/成本评估 |

阶段可部分并行，但以下依赖不可跳过：协议兼容样本先于 Go 网关；标准消息模型先于 AI 自动回复；数据删除链路先于长期记忆生产使用。

## 第一条可运行链路

首个工程目标不是完整后台，而是一条可自动测试的闭环：

```text
脱敏二进制样本
  → Go 读取四字节帧
  → Protobuf 解码 TransportMessage
  → 转成标准入站事件
  → 测试业务处理器生成出站命令
  → Protobuf 编码
  → PHP 兼容解码验证
```

这条链路通过后再接真实测试设备，避免把协议错误和网络环境问题混在一起调试。

## 近期任务顺序

1. `TASK-0002`：旧源码安全、依赖、许可证和迁移审计。
2. `TASK-0003`：恢复 `TransportMessage`、认证、心跳、好友消息和发送任务的最小 `.proto`。
3. `TASK-0004`：建立 Go module、帧解析和 Protobuf 回放测试。
4. `TASK-0005`：连接真实测试设备，验证鉴权、心跳、断线和消息收发。
5. `TASK-0006`：定义标准事件契约及 PHP 业务桥接。
6. `TASK-0007`：引入 PostgreSQL、Redis Streams 和可靠 outbox。
7. `TASK-0008`：接入首个低成本分类模型和人工确认式回复。

后续任务在前一验收门完成后再细化，避免基于错误协议或错误业务假设提前建设。
