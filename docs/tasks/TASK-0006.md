# TASK-0006：旧 APK 兼容的多设备鉴权

状态：进行中（任务 1—5 实现；注册表启动接线待任务 6）
负责人：Codex
开始日期：2026-08-20
最后更新：2026-08-20

## 背景

已分发的 AI 销售 APK 不受项目方控制，无法要求其升级、重装、增加设备密钥或改用 TLS。旧 PHP 实现已确认将 `DeviceAuthReqMessage.Credential` 直接视为设备编号，而不是可以保密的密码。原系统没有可复用的管理后台，但旧数据库可作为一次性迁移证据；新系统不得在运行时依赖旧数据库。

## 目标

- 保持旧 APK 的 TCP/Protobuf `1010 -> 1011` 鉴权协议不变。
- 使用独立 PostgreSQL 设备注册表替代单设备本地配对文件。
- 通过一次性、只读、可重试的迁移导入旧设备授权记录，随后彻底断开旧库依赖。
- 支持多设备独立启用、停用、过期、会话 Token 和单连接接管。
- 不持久化明文 Credential、AccessToken、客户消息或连接源地址。
- 对旧 APK 无法修复的弱鉴权和明文传输风险设置明确的运营边界。

## 不在范围

- 修改、重签名或重新分发旧 APK。
- 实现 APK 无法使用的 TLS、挑战应答或独立设备私钥。
- 在本任务中完成可视化管理后台；首版使用受控管理命令，后续任务再接管理 API/UI。
- 迁移聊天记录、微信号、联系人、旧 Token、旧日志或其他业务数据。
- 为多网关实例实现 Redis 连接目录；首版以单网关、100 台以内为容量目标。

## 风险

- 设备编号不是秘密，无法仅靠服务端防止知道设备编号的人冒充。
- 旧 APK 如果不支持 TLS，设备编号和 Token 可能被同路由监听；公网扩大前必须显式接受该兼容风险。
- Credential 空间如果可枚举，单纯 SHA-256 不能防止离线猜测；正式设计因此使用带服务端 pepper 的 HMAC-SHA-256 作为查询指纹。
- 迁移工具能读取真实设备编号，只允许在服务器受控环境运行，不得产生导出文件或调试日志。
